# DevSecOps Infrastructure

This documentation provides insights and a step-by-step explanation on how to use and configure the Azure Infrastructure as Code (IaC) and Continuous Integration / Continuous Deployment (CI/CD) pipelines for the CerviLog project.

## Overview
This IaC is designed specifically for the healthcare system CerviLog. The system comprises 3 main architectural layers: Presentation, Application, and Persistence. It must meet strict security requirements and integrate DevSecOps into its SDLC. This project manages the CI/CD pipelines and prepares the underlying, secure infrastructure ready for deployment using Terraform.

## Project Structure
- `iac/`: Contains the Terraform scripts organized by environment. For instance, the Dev environment configuration is located at `iac/environments/dev/`.
- `pipelines/`: Contains the YAML definitions for Azure DevOps pipelines (CI/CD) encompassing building, testing, and deployment workflows.
- `docs/`: Additional reference documentation and earlier manual drafts.

## 1. Manual Azure Infrastructure Setup

*Note: As a full production-ready IaC deployment is beyond the scope of the thesis, the actual Azure infrastructure for this project was set up manually via the Azure Portal. The Terraform scripts provided within the `iac/` directory serve exclusively for testing purposes (e.g., Trivy IaC scans) to demonstrate pipeline security controls.*

Below is the step-by-step documentation for replicating the manual infrastructure setup on the Azure Platform that supports the CerviLog system and its CI/CD workflows.

### 1.1. Resource Group Creation
A dedicated Resource Group must be created to contain all system resources logically.
1. Navigate to **Resource groups** in the Azure Portal.
2. Click **Create**.
3. Select your Subscription.
4. Name the Resource Group (e.g., `rg-cervilog-core`).
5. Select a Region (e.g., `West Europe`).
6. Click **Review + create** -> **Create**.

### 1.2. Azure Container Registry (ACR)
The ACR stores the built Docker images (API and WebUI) generated by the CI pipeline.
1. Navigate to **Container registries** -> **Create**.
2. Select the `rg-cervilog-core` Resource Group.
3. Provide a unique Registry name (e.g., `cervilogacr`).
4. Select the `Basic` SKU (sufficient for development/testing).
5. Click **Review + create** -> **Create**.
6. **Enable Admin Access**: After creation, navigate to the ACR resource -> **Settings** -> **Access keys**. Toggle **Admin user** to **Enabled**. (These credentials map to `ACR_USERNAME` and `ACR_PASSWORD` in the pipeline variables).

### 1.3. PostgreSQL Flexible Server
The relational database used for the Persistence layer.
1. Navigate to **Azure Database for PostgreSQL flexible servers** -> **Create**.
2. Select the `rg-cervilog-core` Resource Group.
3. Provide a Server name (e.g., `psql-cervilog-db`).
4. Select PostgreSQL version (e.g., `15`).
5. Choose the Workload type (e.g., `Development` using `Burstable, B1ms` for cost efficiency).
6. Set the Authentication method (PostgreSQL authentication only).
7. Configure the Admin username and password.
8. **Networking**: Under Networking, configure firewall rules to allow access from Azure services (to allow App Services to connect) or specific client IPs.
9. Click **Review + create** -> **Create**.

### 1.4. App Service Plans
The underlying compute resources for hosting the Presentation and Application layers.
1. Navigate to **App Service plans** -> **Create**.
2. Select the `rg-cervilog-core` Resource Group.
3. Name the plan (e.g., `asp-cervilog-linux`).
4. Select Operating System: `Linux`.
5. Select Region: `West Europe`.
6. Select Pricing Tier: Choose a tier that supports custom containers (e.g., `B1` Basic or `P1v3` Premium depending on load requirements).
7. Click **Review + create** -> **Create**.

### 1.5. App Services (WebUI and API instances)
You need to create separate App Services for the Frontend (WebUI) and Backend (API) across your required environments (Dev, Staging, Prod).

*Repeat the following steps for each required App Service (e.g., `cervilog-webui-dev`, `dev-cervilog-stud`, etc.):*

1. Navigate to **App Services** -> **Create** -> **Web App**.
2. Select the `rg-cervilog-core` Resource Group.
3. Name the App Service (this must match the variable names in the `cervilog-cd-vars` pipeline group).
4. Publish: Select **Docker Container**.
5. Operating System: **Linux**.
6. Region: `West Europe`.
7. App Service Plan: Select the `asp-cervilog-linux` plan created earlier.
8. **Next: Docker**:
   - Options: `Single Container`
   - Image Source: `Azure Container Registry`
   - Select your Registry, and leave the image/tag blank for now (the CD pipeline will configure this).
9. Click **Review + create** -> **Create**.

### 1.6. App Service Configuration (Environment Variables)
For each deployed App Service, you must configure the environment variables required by the application runtime (e.g., Database connection strings).
1. Navigate to the created App Service.
2. Go to **Settings** -> **Environment variables** (or **Configuration**).
3. Add necessary application settings (e.g., `ConnectionStrings__DefaultConnection` pointing to the PostgreSQL server).
4. Save the configuration.

Once these resources are provisioned manually and the Azure DevOps Service Connections and Variable Groups are configured, the CD pipeline (`webApp-CD.yml`) will successfully deploy the Docker containers to these instances.

## 2. CI/CD Pipelines Configuration

Prior to running your pipeline, you need an Azure DevOps Pipeline Agent available (either self-hosted or Microsoft-hosted).

### Azure DevOps Setup
1. **Add** this project to your repository.
2. **Create Pipeline** in Azure DevOps:
   - Navigate to Pipelines -> New Pipeline.
   - Choose your repository.
   - Select "Existing Azure Pipelines YAML file".
   - Select the desired path from the `pipelines/` folder (e.g., `webApp-CI.yml`).
   - Review and save.

### Extensions & Tools Setup

**1. SonarQube Cloud (SAST & Quality):**
- Link your Azure DevOps organization with SonarQube Cloud.
- Install the SonarCloud extension from the VS Marketplace and authorize it.
- Create a Service Connection in Azure DevOps settings using your SonarQube Cloud PAT.

**2. Aquasec Trivy (IaC & Container Security):**
- Install the "Aquasec Trivy" extension from the VS Marketplace.
- Request admin approval if required.
- The pipeline utilizes Trivy automatically upon installation for both filesystem and image scanning.

**3. OWASP ZAP (DAST):**
- Executed via Docker containers in the CD pipeline (`webApp-CD.yml`).
- Requires no Azure DevOps extension, but the build agent must have Docker installed.

**4. Azure Container Registry (ACR) Authentication:**
- Used for building and publishing docker images.
- Ensure the ACR has admin credentials enabled (`az acr update --name <name> --admin-enabled true`).
- Retrieve credentials using `az acr credential show --name <name>`.
- Add these credentials to the Pipeline Variable Groups as outlined below.

## 3. Pipeline Variable Groups Configuration

To execute the pipelines successfully without exposing secrets or hardcoding environment-specific values, configure the following Variable Groups in the Azure DevOps Library. Ensure these groups are linked to your pipelines.

### `cervilog-global-vars` (Global / Shared Configuration)
Shared variables used across all pipelines.

| Variable Name | Description | Secret? |
| :--- | :--- | :---: |
| `SONAR_CONNECTION` | The name of the Azure DevOps Service Connection for SonarCloud. | No |
| `SONAR_ORGANIZATION` | The SonarCloud Organization name. | No |
| `SONAR_PROJECT_KEY` | The primary SonarCloud project key (WebApp/Core). | No |
| `SONAR_PROJECT_NAME` | The primary SonarCloud project name. | No |
| `SONAR_API_PROJECT_KEY` | *(Optional)* Dedicated Sonar key for the Mobile API context. | No |
| `SONAR_API_PROJECT_NAME` | *(Optional)* Dedicated Sonar name for the Mobile API context. | No |
| `SONAR_TOKEN` | Token to authenticate API requests downloading Sonar reports. | **Yes** |
| `AZURE_SERVICE_CONNECTION`| Azure Resource Manager (ARM) Service Connection name. | No |

### `cervilog-acr-vars` (Container Registry Secrets & Config)
Specifically for pipelines that build and push Docker images to the Azure Container Registry (ACR).

| Variable Name | Description | Secret? |
| :--- | :--- | :---: |
| `ACR_NAME` | The base name of the ACR instance. | No |
| `ACR_LOGIN_SERVER` | The full FQDN of the Azure Container Registry. | No |
| `ACR_USERNAME` | Service Principal or Admin username for ACR login. | No |
| `ACR_PASSWORD` | Password or Service Principal secret for ACR. | **Yes** |
| `ACR_REPOSITORY` | The repository name for the API/Backend container. | No |
| `ACR_REPOSITORY_UI` | The repository name for the Frontend/UI container. | No |

### `cervilog-cd-vars` (Continuous Deployment & Environment Config)
Defines where containers are deployed and where DAST scans occur within `webApp-CD.yml`.

| Variable Name | Description | Secret? |
| :--- | :--- | :---: |
| `ENV_DEV` | Name of the Development ADO Environment. | No |
| `ENV_STAGING` | Name of the Staging ADO Environment. | No |
| `ENV_PROD` | Name of the Production ADO Environment. | No |
| `API_APP_DEV` | App Service name for the API in Dev. | No |
| `WEBUI_APP_DEV` | App Service name for the UI in Dev. | No |
| `API_APP_STAGING` | App Service name for the API in Staging. | No |
| `WEBUI_APP_STAGING` | App Service name for the UI in Staging. | No |
| `API_APP_PROD` | App Service name for the API in Prod. | No |
| `WEBUI_APP_PROD` | App Service name for the UI in Prod. | No |
| `DEV_APP_URL` | Base URL used by ZAP scanner in Dev environment. | No |
| `STAGING_APP_URL` | Base URL used by ZAP API scanner in Staging environment. | No |
| `STAGING_UI_URL` | Base URL used by ZAP Full UI scanner in Staging environment.| No |
